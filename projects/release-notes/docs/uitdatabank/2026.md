# 2026 Deployments

## Upcoming

These BOA-features are currently being tested and are under active development. Would you like to start using them? Please contact <technical-support@publiq.be>.

✨ **New features**

* Introduction of `departurePlaces` on events. Integrators can link up to 20 places that an event departs from, using `PUT /events/{id}/departure-places` or as part of the event `POST` / `PUT` body. Departure places are also indexed and filterable in Search API via the `q` parameter and the `departurePlaces[]` URL parameter.
* Introduction of a `hasOvernightStay` boolean on subEvents for events of type `Kamp of vakantie` (term `0.57.0.0.0`). The flag is automatically reset when the event type changes to something other than `Kamp of vakantie`. Overnight stays are also indexed and filterable in Search API via the `hasOvernightStay` URL parameter on `/events` and `/offers`.
* Introduction of `openingHoursAdjustedDays` on events and places. Integrators can declare adjusted opening hours for specific periods (start date, end date, opening hours, optional translated description). Validated for overlap and for falling within the calendar range.
* Introduction of `faqs` items on events. Integrators can manage FAQs with the new endpoint `PUT /events/{eventId}/faqs` and include `faqs` in the event `POST` / `PUT` body.
* Introduction of `childcare` times. For events with a `single` or `multiple` calendar, `childcare` can be set per subEvent. For events with a `periodic` or `permanent` calendar, `childcare` can be set per `openingHours` item. Childcare start must be before the event/opening time and childcare end must be after the event/closing time. The `lg` and `xl` calendar summaries mention the childcare, on a line of its own in the textual representation and as a nested list in the HTML one. In Search API the childcare hours extend the period an event is available, so the date and local time filters match an event during its childcare hours as well as during the activity itself.
* Introduction of `openingHoursClosedDays` on events and places, to declare exceptional closed periods on top of the regular calendar.
* New boolean field `childrenOnly` on events, indicating an event aimed specifically at children. Integrators can manage it with `PUT /events/{eventId}/children-only` or as part of the event `POST` / `PUT` body. It must be `true` before `departurePlaces` can be set. Unlike other optional properties, `childrenOnly` is not reset when it is left out of a full `PUT /events/{eventId}` body: the current value is kept, and disabling it requires explicitly sending `false`. When `false` it is omitted from the event `GET` response. Also indexed and filterable in Search API via the `childrenOnly` URL parameter on `/events` and `/offers`.
* Introduction of `birthdateRange` on events. Integrators can manage the birth-date range of the target audience with the new endpoints `PUT /events/{id}/birthdate-range` and `DELETE /events/{id}/birthdate-range`. Birthdate ranges are also indexed and filterable in Search API, via the `birthdateRangeFrom` and `birthdateRangeTo` URL parameters and the `birthdateRange` field in the `q` parameter. A `birthdateRange` and a `typicalAgeRange` are mutually exclusive: sending both in one event body returns a `400`, and setting one on its own endpoint removes the other. An event with a `birthdateRange` therefore has no `typicalAgeRange`, where it used to fall back to `-`, but Search API keeps exposing the matching age range as `typicalAgeRangeConverted`.
* Introduction of a fifth calendar summary size `xl`, next to the existing `xs`, `sm`, `md` and `lg`. It adds the `openingHoursAdjustedDays` and the `openingHoursClosedDays` to the `lg` summary, which only mentions that the hours can differ during those periods, so it is mostly useful on a detailpage of an event or place with calendarType `periodic` or `permanent`. For calendarType `single` and `multiple` the `xl` summary is the same as the `lg` one. Available in Search API through `embedCalendarSummaries[]=xl-text` / `xl-html`, and in Entry API through the `size` parameter of `GET /events/{id}/calendar-summary` and `GET /places/{id}/calendar-summary`.

## July

🛠 **Improvements**

* Following an Elasticsearch upgrade, negative boosting in Search API's advanced queries is no longer supported and has been removed from the documentation. Negative boosting was rarely used; positive boosting is unaffected.

## April

🛠 **Improvements**

* Search API now accepts query bodies through `POST` in addition to `GET` parameters, allowing larger and more complex queries.

🐛 **Bugfixes**

* Fixed `id` and `location.id` projections to consistently use the plural URL form.

## March

🛠 **Improvements**

* ISO-8601 datetimes without an explicit timezone are now accepted and interpreted as `Europe/Brussels`.
* Improved duplicate place detection: when creating a place, and receiving a 400 status code because a duplicate places hit, we  always returns a suggested `id` for the canonical place.



## February

🛠 **Improvements**

* API keys for legacy integrations are now matched to Keycloak client IDs, with logging for unmatched keys, in preparation for the deprecation of API keys in favour of client credentials.


## January

✨ **New features**

* Image upload now supports a JSON body with an online URL (`POST /images` with a JSON body containing the image URL), in addition to the existing `multipart/form-data` upload.
